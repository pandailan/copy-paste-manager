# App Review response plan — v2.0.5 (2), Submission 4a172601-669f-4d86-abfd-9f3c10688897

Review date: July 26, 2026. Two issues were raised. They need different strategies:
**fix the first one, defend the second one.**

---

## Issue 1 — Guideline 2.4.5(iii): auto-launch at startup without consent

**Do not argue this one. Fix it.** Apple is consistent here and an appeal will not win.

### Required app changes

- [ ] Launch-at-login must default to **OFF** on a fresh install.
- [ ] Only call `SMAppService.mainApp.register()` after the user explicitly opts in
      (an unchecked checkbox in Settings and/or onboarding — never pre-checked).
- [ ] If onboarding offers it, the wording must make clear what happens:
      "Start Copy Paste Manager automatically when you log in" with the choice
      defaulting to no.
- [ ] Unregister (`SMAppService.mainApp.unregister()`) immediately when the user
      turns the toggle off.
- [ ] Verify with a clean account/VM: install → first launch → reboot → the app
      must **not** be running. macOS also posts a "added as a Login Item"
      notification the moment `register()` is called — if the reviewer sees that
      on first launch without having touched a toggle, it is an automatic
      rejection. Registration must be reachable only through the user's click.

### Testing note

TCC and login-item state survive app deletion. Test on a fresh user account or
reset between runs:

```
tccutil reset Accessibility <bundle-id>
```

and remove the login item from System Settings → General → Login Items before
re-testing first-run behavior.

### Reply text for App Store Connect (Issue 1)

> We have revised the app so that nothing runs automatically at startup or
> login without explicit user consent. Launch at Login is now disabled by
> default for all new installations. The app only registers itself as a login
> item (via SMAppService) after the user actively enables the "Launch at
> Login" option in Settings, and it unregisters immediately if the user turns
> the option off. On a clean installation, the app performs no registration
> and does not run at login.

## Issue 2 — Guideline 2.4.5: Accessibility used to "paste clips into other apps"

This rejection is routinely issued to clipboard managers and is routinely
overturned — clipboard managers with identical direct-paste functionality are
distributed on the Mac App Store today. The winning pattern is:
(a) make the permission strictly optional in the product, and
(b) reply with a precise technical explanation, then escalate to the
App Review Board if the reviewer doesn't budge.

### Product hardening (do these before/with the reply)

- [ ] The app must be **fully functional without** Accessibility permission:
      copying a clip to the clipboard always works; the user can paste manually
      with ⌘V. Direct paste is an optional enhancement, not a requirement.
- [ ] Never prompt for Accessibility at launch or during onboarding. Only
      surface it when the user explicitly triggers or enables direct paste,
      preceded by an in-app explanation screen describing exactly what it is
      used for and stating it is optional.
- [ ] If permission is not granted, degrade gracefully: copy the clip and show
      a hint ("Copied — press ⌘V to paste"), never a blocking error.
- [ ] Make sure the feature does nothing except synthesize a ⌘V keystroke into
      the frontmost app at the user's request. No observation of other apps'
      UI, no reading of other apps' content via AX APIs.

### Reply text for App Store Connect (Issue 2)

> Thank you for the review. We believe the app's use of Accessibility is
> appropriate and would like to explain.
>
> 1. The permission is strictly optional. Copy Paste Manager is fully
>    functional without Accessibility access: users can copy any clip to the
>    clipboard and paste it themselves with ⌘V. The app never requests the
>    permission at launch. It is only offered when the user explicitly enables
>    the optional "direct paste" convenience, after an in-app screen explains
>    what the permission is used for and that it can be declined.
>
> 2. The feature is user-initiated and minimal. When the user picks a clip and
>    chooses to paste it, the app synthesizes a single ⌘V keystroke into the
>    frontmost application — exactly the action the user would otherwise
>    perform by hand. Posting such an event requires Accessibility
>    authorization (CGEvent / AXIsProcessTrusted); macOS provides no
>    alternative API for this. The app does not observe, read, or control any
>    other application's interface, and uses no other Accessibility
>    capability.
>
> 3. This reduces repetitive manual input — selecting, switching apps, and
>    re-pressing shortcuts many times in a row — which is a genuine benefit
>    for users with motor impairments as well as heavy clipboard users.
>
> Direct paste is a core expectation for a clipboard manager, and this
> mechanism is the established, minimal way to provide it on macOS. We have
> also filed an enhancement request via Feedback Assistant (FB________)
> requesting a scoped, purpose-built API for paste insertion, per your
> suggestion.
>
> We respectfully ask that you re-review the app with this context. We are
> happy to provide a demo video showing that the app is fully usable with the
> permission denied.

Fill in the FB number: actually file the Feedback Assistant enhancement request
("scoped API to insert clipboard content into the frontmost app without full
Accessibility access") before sending — it costs ten minutes and reviewers
respond well to it being real.

### Attach a demo video

Record a short screen capture showing:
1. Fresh launch — no permission prompts.
2. Copying and using history with Accessibility denied (manual ⌘V works).
3. User enabling direct paste → in-app explanation → System Settings grant.
4. Direct paste doing nothing but inserting the clip at the cursor.

Reviewers frequently approve on the strength of exactly this video.

### If the reviewer rejects again — App Review Board appeal

Appeal at https://developer.apple.com/contact/app-store/?topic=appeal
Keep it short and factual:

> We are appealing the Guideline 2.4.5 rejection of Copy Paste Manager
> v2.0.5 (submission 4a172601-669f-4d86-abfd-9f3c10688897). The app uses
> Accessibility authorization solely to synthesize a user-initiated ⌘V
> keystroke — the only macOS mechanism for a clipboard manager to insert a
> selected clip into the frontmost app. The permission is optional, requested
> only after an explicit in-app explanation, and the app is fully functional
> without it. Clipboard managers offering this same direct-paste capability
> are currently distributed on the Mac App Store, so we believe this
> functionality is consistent with existing App Store practice. We have filed
> FB________ requesting a purpose-built API. We ask the Board to review the
> functionality directly; a demo video is available on request.

Notes on the appeal:
- Avoid naming competitor apps in the first reviewer reply (reviewers are
  trained to say "we don't discuss other apps"); the "currently distributed on
  the Mac App Store" phrasing makes the point without inviting that response.
  In a Board appeal you can be more direct if asked.
- Do not bundle Issue 1 into the appeal. Ship the launch-at-login fix in the
  same resubmission so the only open question is the Accessibility one.
